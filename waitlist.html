作業三：海大餐廳候位系統

GitHub Pages 前端 · Google Apps Script 後端 · Queue 自己寫 · Gmail 自動通知 · 不用架伺服器、不用資料庫、不用安裝套件

一、作業目標 · 二、系統規劃 · 三、部署步驟 · 四、程式功能要求 · 五、報告要求 · 六、繳交內容 · 七、評分標準 · 八、注意事項
先玩玩看：顧客候位頁 與 員工管理頁（示範模式，資料只存在你的瀏覽器，員工密碼 staff）。

一、作業目標

整合作業一（Gmail 自動寄信）與作業二（QR Code 導引網頁），做出一套直接放在 GitHub 上運作的餐廳線上候位系統，不需要在電腦上架伺服器、不需要安裝任何套件、不需要資料庫，候位 Queue 自己寫：

  • 顧客掃描餐廳門口的 QR Code 進入候位網頁，填寫姓名、性別、E-mail，取得候位號碼，並隨時看到目前候位組數與自己前面還有幾組。
  • 員工輸入密碼進入管理頁面，看到候位 queue，按「通知」自動寄 E-mail 給輪到的顧客，按「入座」或「取消」將該組移出 queue。

課程提供完整範例（前端 3 個檔案 + 後端 1 個檔案），同學可以直接部署、修改，或參考其寫法自行重寫。

3. Queue 資料結構（自己寫）

Queue 是一個 JSON 陣列，依加入順序排列，越前面越早候位。整個陣列以字串存在 PropertiesService 的 queue 這個 key 裡，另外用 next_id 記下一個號碼。

[
  {"id": 7, "name": "王小明", "gender": "男", "email": "a@gmail.com", "party_size": 2,
   "status": "waiting",  "created_at": "2026-10-23 12:00:05", "notified_at": ""},
  {"id": 8, "name": "李小華", "gender": "女", "email": "b@gmail.com", "party_size": 4,
   "status": "notified", "created_at": "2026-10-23 12:03:40", "notified_at": "2026-10-23 12:20:00"}
]
方法作用說明
enqueue(item)加入候位取 next_id 當號碼，push 到陣列尾端
find(id)找某號碼回傳該筆資料
positionOf(id)前面還有幾組該號碼在陣列中的索引值
update(id, fields)更新狀態通知後把 status 改成 notified
remove(id, reason)移出隊伍splice 掉該筆，並把當日 seated / cancelled 計數 +1
stats()今日統計回傳 {seated, cancelled}

狀態只有兩種留在 queue 裡：waiting（等候中）、notified（已通知）。入座或取消的直接移出，不佔隊伍。

限制：PropertiesService 一個值最多 9KB，約可放 50 組；超過時 enqueue 會回「候位已滿」。這對課堂測試足夠，若要更大可改用多個 key 或外部儲存（加分題）。

4. API（前端用 fetch 呼叫 Apps Script，全部回 JSON）

action方法誰用參數功能
countGET顧客頁無目前候位組數
statusGET顧客頁id某號碼的狀態、前面幾組
joinPOST顧客頁name, gender, email, party_sizeenqueue，回傳號碼
leavePOST顧客頁id顧客自行取消（remove）
queueGET員工頁key整個 queue 與今日入座 / 取消數
notifyPOST員工頁key, id寄通知信，狀態改 notified
seatPOST員工頁key, id入座，remove
cancelPOST員工頁key, id員工取消，remove
logGET員工key最近 40 筆事件紀錄（候位、通知、入座、取消），寫報告用
resetGET員工key清空所有資料（測試完用）

員工操作都要帶 key（員工密碼），後端核對 Code.gs 裡的 STAFF_KEY。POST 不設定 Content-Type（瀏覽器預設 text/plain），因為 Apps Script 不支援 CORS preflight。

5. 示範模式

app.js 的 API_URL 留空時為示範模式：前端自己用 localStorage 跑一個一樣的 Queue，可以先把畫面與流程走一遍，但不會跨裝置、也不會真的寄信。部署好後端並填入 API_URL 後才是正式模式。

三、部署步驟

A. 後端（Google Apps Script）

  1. 用自己的 Google 帳號打開 script.google.com → 「新專案」。
  2. 把範例 Code.gs 的內容全部貼進去取代原本內容，把 STAFF_KEY 改成自己的員工密碼，專案命名為「候位系統」。
  3. 右上角「部署」→「新增部署作業」→ 類型選「網頁應用程式」。執行身分：我　／　誰可以存取：所有人。
  4. 第一次會要求授權（代替你寄信），按允許。
  5. 複製「網頁應用程式網址」（結尾是 /exec）。
  6. 在瀏覽器直接打開 該網址?action=count，看到 {"waiting":0} 就代表後端成功。
  7. 之後每次修改 Code.gs，要「部署」→「管理部署作業」→ 編輯 → 版本選「新版本」→ 部署，網址才會更新內容。

B. 前端（GitHub Pages）

  1. 在 GitHub 建立公開儲存庫 你的帳號.github.io（已經有的就直接用）。
  2. 把範例的 waitlist 資料夾（index.html、staff.html、app.js、waitlist.css）放進去。
  3. 把 app.js 的 API_URL 改成步驟 A 的網址，RESTAURANT 改成自己的餐廳名稱。
  4. push 上去，約一分鐘後 https://你的帳號.github.io/waitlist/ 就是顧客頁，/waitlist/staff.html 是員工頁。
  5. 用作業二的程式把顧客頁網址做成 QR Code： 
    python qr_web.py make --url https://你的帳號.github.io/waitlist/ --out qr_waitlist.png --label "海大餐廳 候位"

五、報告要求

報告使用 Word、PDF 或 Markdown 皆可，必須包含以下三部分，缺一項即扣分。

1. 報告題目

自訂一個能表達本次作業內容的題目，例如：「以 GitHub Pages 與 Google Apps Script 實作海大餐廳線上候位系統」。不可直接寫「作業三」或「候位系統報告」。

2. 目的

說明傳統紙本或現場叫號候位有什麼問題、本系統如何解決（顧客不必在門口等、輪到時自動通知）、為什麼選擇 GitHub Pages 加 Apps Script 這種不用架伺服器與資料庫的做法，以及預期達成的效果。建議 150 到 250 字。

3. 報告內容項目（全部必須依實際執行結果撰寫）

以下每一項都要有自己實際跑出來的證據（網頁截圖、手機截圖、收到的 E-mail 截圖、?action=log 的輸出）。抄範例、憑想像寫的結果一律不計分。
項目必須包含的內容
3.1 執行環境使用的 GitHub 帳號與網站網址、Google 帳號（可部分遮蔽）、測試用手機型號與數量、瀏覽器
3.2 系統規劃自己畫的架構圖與流程圖、API 清單（可依本說明修改，但要和自己的程式一致）
3.3 Queue 設計說明自己的 Queue 用什麼資料結構、enqueue / remove / positionOf 怎麼寫、資料存在哪裡、有什麼限制。要貼自己的程式碼片段並逐段說明
3.4 部署過程Apps Script 部署設定截圖（執行身分、存取權限）、?action=count 的結果、GitHub Pages 上線截圖
3.5 前後端溝通說明前端三個檔案各做什麼、fetch 如何呼叫後端、為什麼 POST 不能設定 Content-Type
3.6 顧客端實測手機掃 QR Code 進入、填表、取得號碼、看到前面幾組的截圖，至少 3 組不同顧客（可由同學手機扮演）
3.7 員工端實測員工登入、候位 queue 表格截圖，至少含 3 組候位；密碼錯誤時的畫面
3.8 通知功能實測員工按「通知」後的提示訊息、顧客手機收到的 E-mail 截圖、顧客端狀態變為「已通知」的截圖
3.9 入座 / 取消實測入座後 queue 減少、後面顧客的「前面幾組」跟著減少的前後對照截圖
3.10 事件紀錄?action=log&key=密碼 的完整輸出，說明這次測試共幾組候位、幾次通知、幾組入座、幾組取消
3.11 錯誤與排除實際遇到的錯誤（例如 Apps Script 未授權、部署權限設成「只有我」導致前端讀不到、改了 Code.gs 忘記建新版本、填錯 API_URL）、原因與解法。若完全沒遇到錯誤，請故意把 API_URL 改錯一個字再操作，記錄系統的反應
3.12 結論與心得系統是否達成目的、若真的放在餐廳使用還缺什麼（例如防止重複取號、資料隱私、50 組上限）、學到什麼

八、注意事項

  • Apps Script 部署成「所有人可存取」後，任何知道網址的人都能呼叫 API。員工密碼不要用預設的 staff，作業結束後請到「部署」把它封存。
  • Queue 裡有同學的 E-mail，作業結束後請呼叫 ?action=reset&key=密碼 清空。
  • 測試用的顧客 E-mail 請用自己或同組同學的信箱，不要寄給不相關的人。
  • MailApp 一般 Gmail 帳號每天只能寄 100 封，測試時不要狂按「通知」。
